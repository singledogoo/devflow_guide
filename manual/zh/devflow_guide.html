00 · GUIDE MAP

先理解这套 Skill 实际解决什么问题

一个工程如果只有源码，容易出现“需求不清、模块接口反复变化、测试无法复现、文档与代码脱节、PR 合并后被误认为已经发布”的情况。devflow_guide 把这些问题拆成需求、架构、接口、任务、代码、验证、评审、发布八类对象，并为它们建立一致的关系。

设计有边界先确认需求、环境、约束和风险，再做足够的架构设计；避免为了“规范”过度设计。
实现有证据每次改动能追踪到需求和测试。构建成功与实板验证、PR 合并与正式发布明确区分。
存量项目友好先分析现有文件，识别真正权威的文档。初始化只新增缺失的治理文件，不覆盖原文件。
学习顺序：第一次使用建议阅读 01→04→07→08；准备架构调整时重点阅读 03、05；准备 PR 或正式发布时阅读 08、09。术语解释见末尾，可随时通过目录跳转。
01 · INSTALLATION

安装 Skill：先让 Agent “看见”治理规则

Agent Skills 是由 SKILL.md 和可选的 references/、scripts/、assets/ 组成的目录。当前包采用规范兼容的 Skill 目录名 devflow-guide（连字符），对外名称仍为 devflow_guide。名称字段不能包含下划线，且必须与 Skill 文件夹同名。

1. 解压后的文件结构

ZIP 文件结构 
devflow_guide_bundle/
├── README.md
├── devflow-guide/                    ← Skill 根目录
│   ├── SKILL.md                     ← 触发条件与工作流程
│   ├── references/                  ← 分类/阶段/审查/示例
│   ├── assets/templates/            ← 文档模板
│   ├── scripts/devflow.py           ← 识别/初始化/审查/门禁
│   └── scripts/test_devflow.py      ← 离线自测
├── manual/
│   ├── zh/devflow_guide.html            ← 中文手册
│   └── en/devflow_guide.html            ← English manual
└── examples/                        ← 示例配置/追踪关系

2. 推荐安装到 Codex 项目

将解压后的整个 devflow-guide 文件夹复制到项目根目录的 .agents/skills/ 下。不要只复制 SKILL.md，否则模板和工具脚本不可用。也可以安装到个人目录 ~/.agents/skills/，让多个项目共用。

安装完成后的项目路径
your-project/
└── .agents/
    └── skills/
        └── devflow-guide/
            ├── SKILL.md
            ├── references/
            ├── assets/
            └── scripts/
注意：这里的安装只是让兼容的开发代理能够发现规则，不会自动替你修改仓库。不同 Agent 的技能加载位置可能不同；Codex 仓库级推荐路径为 .agents/skills/devflow-guide/。

3. 首次向 Codex 提交的任务

可直接复制给开发 Agent 
请使用 $devflow-guide。
先只读检查当前仓库，不修改任何代码与文档。
识别项目属于 embedded / web / app / hybrid 中哪类，
根据故障影响建议 lite / standard / high 等级。
列出现有权威文档、代码目录、构建测试入口、缺口与风险。
提交一份接管方案，包含拟新增文件与不触碰的现有文件。
未得到我的明确批准前，只允许 inspect 与 init --dry-run。
02 · PROJECT PROFILING

识别项目类型，确定“管控强度”

所谓 项目类型（profile） 是根据运行环境和交付物对流程进行分流；质量等级（assurance） 是根据故障后果、外部约束及恢复成本决定要保留多少设计和验证证据。两者是不同维度，不应该根据文件扩展名或代码量直接判断。

等级适用条件可做的合理裁剪不能省略的原则
lite个人工具、概念验证、低风险实验把一些详细设计写在 Issue；减少独立模板数量需求可测试、变更有边界、不虚构结果
standard多人维护、实际用户、需要持续交付只为重要决策写 ADR；测试按风险分层PR/CI、接口兼容、文档与测试同步
high故障代价高、数据不可逆、涉及安全或合同追踪可裁剪无关文档，不能减掉必要证据双向追踪、受控基线、独立评审与明确授权

混合项目怎么做：例如一套系统同时存在 RK3588 设备侧、Web 后台和 Qt 上位机，应先定义它们之间的系统契约，再分别对每个子项目应用 profile。不能让 Web 的 E2E 结果替代设备端的 HIL 结果。

03 · LIFECYCLE

开发闭环：每个阶段都必须有“可检验的退出条件”

开发流程不是一次走完的瀑布。推荐对每个独立可验证的功能重复以下小循环。点击节点查看它的目的、产物、常见错误；“自动演示”仅用于理解流转。

需要主动验证一个阶段是否真正完成，而非只检查是否存在文档。
阶段典型工作可交付证据
需求定义目标、成功条件、边界和失败路径REQ / 验收条件
风险验证验证最高不确定性：板卡吞吐、并发、迁移、安全等PoC/测量结果、风险处置
架构模块职责、接口方向、运行数据流、重要取舍架构图和必要的 ADR

任务独立切片、依赖、验收、范围与测试TASK / Issue

04 · DOCUMENTS AS CODE

文档、代码和测试为什么要同时变化

文档即代码（Docs as Code）指需求、架构和接口文档像源码一样保存版本、参与变更审查，并能通过脚本做基本一致性检查。核心不是增加文档数量，而是让一份需求、一个权威契约、一组测试以及对应变更记录互相找得到。

REQ 需求
→
ADR / 设计
→
TASK / PR
→
TEST / 证据

1. 需求如何写成可测试的要求

不建议

“ISP 仿真软件性能要高，参数调节要实时，结果要稳定。”

没有运行环境、输入大小、时间统计方法、门槛与异常定义。
更合理的演示写法

“REQ-ISP-001：在指定测试机与输入 RAW 图规格下，将 Gamma 调节后预览更新的 99 分位耗时限制在经评审确定的门槛内，使用统一基准脚本连续测量并归档原始结果。”

具体数值、设备及负载必须由项目实测或业务目标决定；这里不伪造指标。

2. 一条追踪记录如何跨越多种工件

TRACEABILITY.csv · 示例，不是实际通过证明 
requirement_id,design_ref,test_id,evidence_ref,status
REQ-ISP-001,docs/devflow/architecture/ARCHITECTURE.md,TEST-ISP-001,,planned

这里的 REQ-ISP-001 是需求标识；design_ref 指向唯一的设计文件；TEST-ISP-001 是测试用例标识；evidence_ref 未填说明没有验证证据；planned 表示测试已规划。不能把 planned 改成 verified 以便让审查通过。

3. 什么变化必须评估文档影响

代码变化至少评估的关联资料典型回归
修改接口/API接口契约、调用方、需求、ADR（如重大决策）契约测试、兼容性负测
修改驱动 Buffer/DMA内存协议、时序、硬件矩阵数据完整性、多次启停、实板 HIL
修改数据库表数据模型、迁移计划、回滚方案迁移/恢复与兼容
修改 Qt 异步渲染线程/状态机、资源生命周期、错误恢复关闭重开、压力与系统兼容
修正文案或内部日志按实际影响判断；不强制改架构相关轻量检查
05 · STRUCTURE CONTROL

目录管控：能新增治理能力，但不破坏成熟仓库

一套高可靠工程目录不意味着必须把所有代码搬到统一命名的目录。已有工程的构建脚本、模块层次和权威文档应优先保留。Skill 默认采用 docs/devflow/ 承载需要新增的治理文档，使用 .devflow.json 记录文档映射（authoritative document map）。

典型新增文件（standard / 嵌入式）
repo/
├── .devflow.json                         ← 项目级约束配置
├── docs/devflow/
│   ├── INDEX.md                          ← 工程治理入口
│   ├── requirements/REQUIREMENTS.md       ← 可验证需求
│   ├── architecture/ARCHITECTURE.md       ← 组件、数据流、质量预算
│   ├── interfaces/CONTRACTS.md            ← 唯一权威接口的引用
│   ├── testing/TEST_PLAN.md               ← 测试策略与环境
│   ├── testing/TRACEABILITY.csv           ← REQ→设计→TEST→证据
│   ├── reviews/REVIEW_LOG.md              ← 审查和待办
│   ├── release/RELEASE_PLAN.md            ← 版本/回滚
│   └── embedded/                          ← 板卡、DMA、HIL、固件
├── [原有代码和构建目录]                  ← 初始化不碰
└── [原有 CI / .git]                     ← 初始化不碰

如仓库已经有 docs/ARCHITECTURE.md，使用 init --adopt 时会优先尝试映射已有文件，不新造第二份冲突架构文档。若历史目录不符合自动识别规则，则需要人工修改 .devflow.json 的路径，保持一个权威来源。

按照可靠性等级增减文档

不允许自动执行的破坏性操作：覆盖已存在的需求/架构文档、移动源码目录、修改构建配置、改写 Git 历史、设置远端分支保护、直接发布固件/线上服务。此类操作必须另有明确授权和专项验证。
06 · DOMAIN-SPECIFIC CONTROLS

嵌入式、Web 和应用软件：相同骨架，不同风险

嵌入式工程核心关注硬件版本、时钟/供电/复位、驱动生命周期、DMA/Cache、实时性、真实板卡测试、烧录与升级恢复。
Web 工程核心关注接口协议、身份认证与授权、数据迁移、并发和安全边界、E2E、可观测性以及服务恢复。
桌面/移动应用核心关注 UI 状态、线程/生命周期、不同 OS 和设备兼容、安装/更新/卸载、数据保护与崩溃恢复。

完整专项管理差异

问题嵌入式Web应用软件
真实运行环境目标板、PCB 修订、BSP、固件浏览器/API/DB/云与网络OS、GPU/驱动、设备权限
关键设计资料原理图、接口时序、内存所有权API Schema、信任边界、数据模型UI 状态、事件循环、数据与插件模型
主要风险Cache 错误、错帧、时序、断电越权、迁移失败、容量与隐私卡顿、兼容性、升级丢数据
核心验证Host + Target + HIL + 长稳/异常Contract + Integration + E2E + 负载/安全Unit + UI + OS 兼容 + 安装升级
发布资产image/DTB/BSP/板卡矩阵和 hash镜像/DB迁移/灰度/监控恢复安装包/签名/支持矩阵/回滚
实例：在 RK3588 上的算法线程单元测试全部成功，并不能证明 Sensor、PCIe、DMA、Cache 与端到端实时性都正常；在 Web 中 API 单测成功也不能证明部署后的权限配置、数据库迁移与登录流程正确。
07 · OPERATION RECIPES

实际使用的四条工作流

A. 新建项目：设计与目录管理先行

命令 · 在解压包中运行；替换路径 
python devflow-guide/scripts/devflow.py inspect --root ./my-project
python devflow-guide/scripts/devflow.py init --root ./my-project \
  --profile embedded --assurance standard --dry-run
# 查看输出、批准新增文件后：
python devflow-guide/scripts/devflow.py init --root ./my-project \
  --profile embedded --assurance standard
python devflow-guide/scripts/devflow.py audit --root ./my-project

首先填充需求、架构、接口和测试策略；警告中的 TODO 表示模板仍未完成。随后由人工确认需要哪些 PoC/板级测试，才开始设计或编码。

B. 已有项目：接管而不是“重新生成”

命令 · 已有仓库必须显式 --adopt 
python devflow-guide/scripts/devflow.py inspect --root ./existing-repo
python devflow-guide/scripts/devflow.py init --root ./existing-repo \
  --profile web --assurance high --adopt --dry-run
# 审查是否映射了已有规范；明确批准后移除 --dry-run
python devflow-guide/scripts/devflow.py init --root ./existing-repo \
  --profile web --assurance high --adopt

如果现有 README.md、SRS、API Schema 或架构文档已经权威，不允许再复制内容形成冲突版本。首先核查 .devflow.json 映射是否正确。

C. 单个功能：需求 → 小任务 → 同 PR 验证

先为功能写 REQ 和验收条件；如果是跨模块接口/架构决策，新增 ADR 或更改契约；然后建立 TASK，限定本轮源文件、测试和文档范围。Agent 实现后执行实际构建/测试，报告未运行部分，产生 PR 给人审查。

审查草稿 
请使用 $devflow-guide 实施 TASK-ISP-007：
1. 先核对当前 main 的 SHA、关联 REQ 和 ADR 状态。
2. 只修改 TASK 指定范围。接口变化要同步修改契约和测试。
3. 按项目现有方式运行实际可执行的构建、单测、集成测试。
4. 报告 PASS / FAIL / UNKNOWN，附命令、环境、真实日志/URL。
5. 不自动合并 PR，也不把 Proposed ADR 当成 Accepted。
6. 提交审查报告：变更文件、风险、缺失证据、下一步。

D. 发布候选：本地预检 + 外部真实门禁

只读自检命令 
python devflow-guide/scripts/devflow.py audit --root ./my-project --strict
python devflow-guide/scripts/devflow.py gate --root ./my-project --stage design
python devflow-guide/scripts/devflow.py gate --root ./my-project --stage merge
python devflow-guide/scripts/devflow.py gate --root ./my-project --stage release

关键差别：脚本能核对本地文件、追踪关系和 Git 状态，但不能认证远程 CI、评审、硬件试验或审批真实性。即使结果是 READY_FOR_HUMAN_REVIEW，仍须在实际 PR、CI 和发布系统完成外部确认。

08 · CLI REFERENCE

内置脚本：哪些是真的自动检查，哪些只能报告未知

devflow.py 使用 Python 3.9+ 标准库，支持 Windows/Linux/macOS。它不调用项目构建命令、不联网、不执行危险的 Git 写操作；所有阶段门禁都只给出本地预检意见。

命令是否写入项目能检查什么不能声称什么
inspect否目录线索、类型建议、Git 基线自动准确理解全部业务
init --dry-run否列出计划建立/映射的文件已经初始化
init [--adopt]仅新增缺失治理文件生成配置和待填写的规范模板需求/设计已获批准
audit否文档映射、路径安全、占位符、追踪 CSV、Git 变更提示测试真实通过、代码语义正确
gate --stage否设计/合并/发布前的结构性门禁获得外部 CI 或人工放行

典型输出如何解释

BLOCKED

存在必需文件缺失、不安全路径、证据缺口或关键占位符。当前不能按该阶段正常推进。

REVIEW_REQUIRED

发现警告或待人工确认项，不能直接视作完全可用。

LOCALLY_CONSISTENT

本地结构检查没有发现问题，但不代表实现、性能或远程 CI 真正通过。

READY_FOR_HUMAN_REVIEW

仅表示可以提交给有权限的人继续审核，不表示正式批准。

退出码和 CI 接入

audit 默认在出现结构错误时返回退出码 2；无错误但有警告通常返回 0，带 --strict 时警告返回 1。gate 阻断时返回 2。建议在 CI 中根据本项目风险选择 audit --strict，但不要用脚本退出码替代真正的测试、PR 审批和发布授权。

如使用 Python 包装脚本或 monorepo，请确保 --root 指向真正的受管范围。检查 .devflow.json 中的 document_map，不要把一份父仓库的 SRS 强行套给无关子模块。
09 · INTERACTIVE GATE LAB

交互理解：为什么“检查清单全打勾”仍不是发布批准

下面是学习用的门禁模拟器。可以切换阶段、勾选证据，观察本地预检如何变化。它不读取实际仓库，也不会改变 Git、CI 或发布状态。

注意：全部勾选后仅为“模拟本地检查就绪”。真实的 CI、目标板测试、授权人员审批仍须独立验证。

证据的四种真实性

来源可信表达例子
实际工具/CI 验证明确对象、环境、SHA、原始结果、来源CI Provider 给出的 run URL 与 commit
真实人工验证审查人、职责范围、证据和时间受权 reviewer 的正式评审记录
自填状态只能记 self-reported手工把 JSON 改成 "passed"
无证据/工具不可用UNKNOWN / BLOCKED无法访问实验室板卡或远程 CI
10 · PRACTICE

三个真实风格场景：怎样落地而不写空文档

案例一：PC 端 ISP 仿真系统

需求：用户可以调节 Gamma 并预览处理结果；当 Gamma 功能关闭时，不应以启用状态的参数规则错误拒绝请求。设计：明确参数生效条件、处理管线输入输出格式、状态变更语义及错误码；若规则跨模块影响较大，再记录 ADR。任务：修改契约/实现/边界测试。验证：覆盖启用/关闭、非法值、切换时状态更新、必要性能指标。发布：构建通过、审查完成不等于已经正式发布新契约。

这个案例的最小追溯链

REQ-ISP-001 → 接口契约中的 enabled 条件 → TASK-ISP-007 → 实现 PR → TEST-ISP-001（正/负例）→ 真实 CI/人工验收记录。编号只是演示。

案例二：RK3588 双路图像采集与处理

需求：在已确认的 Sensor/板卡配置下维持目标帧率，不允许消费者线程落后造成帧回退。架构：生产者-消费者队列、乒乓/环形缓冲、DMA 和 Cache 所有权、时间戳同步、丢帧策略。验证：Host 测试数据结构，实板验证多路帧完整性、长稳、启停、异常中断和温度影响。发布：固定 BSP、内核、DTB、用户固件与板卡修订版的组合。

案例三：Qt H.265 视频播放器

需求：明确支持哪种 H.265 码流/封装、操作系统/解码器环境；失败时给出可恢复错误。架构：播放状态机、解码线程、视频渲染、Buffer 上限和资源释放。验证：各种码流样本、关闭/重开、硬解不可用、设备切换、安装包升级。发布：实际构建的安装包版本必须与应用显示版本一致，验证签名、依赖与恢复路径。

可复用任务合同

Task Contract · 适用三类项目 
TASK_ID: TASK-<SCOPE>-NNN
TYPE: feature / defect / refactor / hotfix / docs
REQ: 关联需求 ID
BASELINE: 基线分支和当前真实 SHA
GOAL: 可观察的结果与价值
SCOPE: 必须修改的模块；明确不修改什么
DESIGN: 架构/ADR/接口契约，及各自状态
ACCEPTANCE: 正常/异常输入与可测指标
TEST: 单元、集成、实板/HIL/E2E 的真实执行条件
RISK: 安全、兼容、数据、时序、升级回退
OUTPUT: 源码 + 必要文档 + 测试 + 证据
STOP: 无法验证、接口冲突、未经授权的危险操作
11 · TROUBLESHOOTING

最容易把“流程管理”做错的地方

是否每次改一行代码都要写一个 ADR？

不需要。ADR 应记录重大的、需要长期记住原因的架构选择。常规小修复在 Issue/PR 中说明即可。详细设计按复杂度和风险决定。

我已有大量资料，为什么不直接套用 Skill 模板？

同一需求或协议不能有两个互相冲突的权威版本。应先以 --adopt --dry-run 查看自动映射，保留现有规范；自动识别不到的路径人工加入 .devflow.json。

检测为 hybrid/ambiguous，该怎么办？

先按具体运行时、交付物、子项目选择作用范围。一个含固件、后端和 Qt GUI 的仓库需要明确跨系统契约，不能自动套用一个 profile。

测试机/目标板暂时无法使用，还可以提交 PR 吗？

应准确标记未运行及其风险；是否可合并由项目门禁和权限所有者决定。高可靠或安全关键变更可能必须阻断。不能把 Host 单测当作 HIL 验证。

为什么发布预检不会输出“自动通过审批”？

发布涉及远程 CI 真实性、制品归属、独立审批、目标环境以及潜在不可逆操作。离线本地脚本不具备这些权限和信息，必须保持 UNKNOWN。

能否采用 Git Flow、Trunk-Based Development 或 Scrum？

可以。这套 Skill 不强制分支模型或敏捷管理方式，而是要求小范围可审查变更、可靠合并门禁、版本基线与可追踪证据。按团队交付约束选择流程。

能否直接用于安全认证（ISO 26262 / IEC 62304 等）？

不能把这个通用 Skill 当作合规证明。受监管项目仍需专门标准、过程体系、工具资格和授权的独立评估；本包只能提供通用工程起点。
