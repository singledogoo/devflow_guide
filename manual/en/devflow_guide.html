Developer Workflow Governance · Practical Guide

Turn software work from "it compiles" into delivery that is designed, verified, and traceable

This is the usage and engineering-practice manual for the devflow_guide skill, not a classroom slide deck. It follows the order of a real software project: what to do, why, what artifact to produce, how to judge completion, and which decisions an AI coding agent can assist but cannot replace.

00 · GUIDE MAP

What this skill actually solves

A repository that contains only source code tends to drift: unclear requirements, interfaces that keep changing, tests that cannot be reproduced, documents that no longer match the code, and a merged PR that gets mistaken for a release. devflow_guide splits that problem into eight objects — requirements, architecture, interfaces, tasks, code, verification, review, and release — and keeps one consistent relationship among them.

Design has a boundaryConfirm the requirement, environment, constraints, and risk before designing just enough architecture. Do not over-design in the name of process.
Implementation has evidenceEach change traces to a requirement and a test. A successful build is not board verification, and a merged PR is not a release.
Existing projects stay intactInspect current files first and identify the real authority. Initialization only adds missing governance files. It does not overwrite originals.
Suggested reading order: first use, read 01, then 04, 07, and 08. Before an architecture change, read 03 and 05. Before a PR or release, read 08 and 09. Terms are at the end; jump from the contents at any time.
01 · INSTALLATION

Install the skill so the agent can see the rules

An Agent Skill is a directory made of SKILL.md plus optional references/, scripts/, and assets/. This package uses the spec-compatible directory name devflow-guide (hyphen). The display name remains devflow_guide. The name field cannot contain underscores and must match the folder name.

Copy the whole devflow-guide folder into .agents/skills/ at the project root. Do not copy only SKILL.md, or the templates and scripts will be missing. To share it across projects, copy it to ~/.agents/skills/.

02 · PROJECT PROFILING

Identify the project type, then set the level of control

Profile routes the workflow by runtime and deliverable. Assurance decides how much design and verification evidence to keep, based on failure consequence, external constraints, and recovery cost. They are different axes. Do not infer either from a file extension or from the size of the codebase.

LevelFits whenReasonable tailoringDo not drop
litePersonal tools, proofs of concept, low-risk experimentsKeep detailed design in the issue; use fewer standalone templatesTestable requirements, a bounded change, and no invented results
standardSeveral maintainers, real users, ongoing deliveryWrite an ADR only for important decisions; layer tests by riskPR and CI, interface compatibility, docs and tests moving together
highCostly failure, irreversible data, safety, or contractual traceabilityUnrelated documents may be omitted; required evidence may notTwo-way traceability, a controlled baseline, independent review, and explicit approval

Mixed systems: a product that has an RK3588 device, a web service, and a Qt host should define the system contract first, then apply a profile to each subproject. A web end-to-end result does not stand in for device HIL.

03 · LIFECYCLE

The development loop: every stage needs a checkable exit

This is not a one-pass waterfall. Repeat the small loop for each independently verifiable change. Select a node to see its purpose, artifact, and common mistake. Auto-play is only a way to see the flow.

Check whether a stage is actually finished, not merely whether a document exists.
StageTypical workEvidence you can deliver
RequirementsGoal, success conditions, boundaries, and failure pathsREQ and acceptance criteria
Risk checkProbe the largest unknown: board throughput, concurrency, migration, securityPoC or measurement, and a risk disposition
ArchitectureModule responsibilities, interface direction, runtime data flow, important tradeoffsArchitecture description and only the ADRs that are needed
InterfacesData structures, timing, error codes, compatibility, and resource ownershipContract, state machine, or sequence description
TasksIndependent slices, dependencies, acceptance, scope, and testsTASK or issue
ImplementationOnly the agreed scope, with the tests and documents that must change with itCode, unit tests, and document diffs
ReviewPull request, code review, build, and static checksReal CI and review records
System verificationPerformance, compatibility, faults, and stability in the real environmentSystem, HIL, or end-to-end evidence
ReleaseFreeze the candidate, record the artifact hash, compatibility, recovery, and approvalRelease record and artifact manifest
MaintenanceWatch issues, review what happened, and feed the next requirementIssues, logs, and regression records
An accepted ADR is not implemented code. A merged PR is not a product release. A passing unit test is not acceptance on real hardware or in production.
04 · DOCUMENTS AS CODE

Why documents, code, and tests change together

Docs as Code means requirements, architecture, and interface documents are versioned like source, reviewed with the change, and given a basic consistency check by script. The point is not more documents. It is that one requirement, one authoritative contract, one set of tests, and the change record can find each other.

REQ
→
ADR / design
→
TASK / PR
→
TEST / evidence

1. Write a requirement that can be tested

Too vague

"The ISP simulator must be fast, parameter changes must be real time, and results must be stable."

No machine, input size, timing method, threshold, or fault definition.
A usable demonstration

"REQ-ISP-001: on the named test machine and RAW input specification, the 99th-percentile preview update after a Gamma change stays within the reviewed threshold, measured by one benchmark script and archived with the raw samples."

The number, device, and load must come from measurement or a business target. This manual does not invent a metric.

2. How one trace row crosses the artifacts

TRACEABILITY.csv · a sample, not proof of a pass 
requirement_id,design_ref,test_id,evidence_ref,status
REQ-ISP-001,docs/devflow/architecture/ARCHITECTURE.md,TEST-ISP-001,,planned

REQ-ISP-001 identifies the requirement. design_ref points at the single design file. TEST-ISP-001 identifies the test. An empty evidence_ref means there is no verification evidence yet. planned means the test is planned. Do not change planned to verified just to make a review look green.

3. Which code changes must revisit documents

Code changeAt least reviewTypical regression
Interface or APIContract, callers, requirements, and an ADR if the decision is significantContract tests and compatibility negatives
Driver buffer or DMAMemory protocol, timing, and the hardware matrixData integrity, repeated start/stop, and on-target HIL
Database tableData model, migration plan, and rollbackMigration, restore, and compatibility
Qt async renderingThreads and state machine, resource lifetime, and error recoveryClose/reopen, stress, and OS compatibility
Copy or an internal logJudge the real impact; do not force an architecture editA small related check
05 · STRUCTURE CONTROL

Add governance without breaking a mature repository

A disciplined layout does not mean moving all code into one naming scheme. Keep the build scripts, module structure, and authoritative documents that already work. By default the skill puts new governance documents under docs/devflow/ and records the authoritative document map in .devflow.json.

Files typically added (standard / embedded)
repo/
├── .devflow.json                         ← project constraints
├── docs/devflow/
│   ├── INDEX.md                          ← governance entry
│   ├── requirements/REQUIREMENTS.md      ← verifiable requirements
│   ├── architecture/ARCHITECTURE.md      ← components, data flow, budgets
│   ├── interfaces/CONTRACTS.md           ← pointer to the one contract
│   ├── testing/TEST_PLAN.md              ← strategy and environments
│   ├── testing/TRACEABILITY.csv          ← REQ to design to TEST to evidence
│   ├── reviews/REVIEW_LOG.md             ← review notes and open actions
│   ├── release/RELEASE_PLAN.md           ← version and rollback
│   └── embedded/                         ← boards, DMA, HIL, firmware
├── [existing code and build tree]        ← init does not touch this
└── [existing CI / .git]                  ← init does not touch this

If the repository already has docs/ARCHITECTURE.md, init --adopt tries to map that file instead of creating a second, conflicting architecture document. If a historical path is not recognized, edit the path in .devflow.json and keep a single authority.

Documents by assurance and profile

Never do these automatically: overwrite an existing requirements or architecture document, move source trees, edit build configuration, rewrite Git history, change remote branch protection, or publish firmware or a live service. Those need a separate explicit authorization and their own verification.
06 · DOMAIN-SPECIFIC CONTROLS

Embedded, web, and applications: one skeleton, different risks

EmbeddedHardware revision, clock, power, and reset, driver lifetime, DMA and cache, real-time behavior, on-target tests, flashing, and upgrade recovery.
WebAPI contract, authentication and authorization, data migration, concurrency and trust boundaries, end-to-end tests, observability, and service recovery.
Desktop and mobileUI state, threads and lifecycle, OS and device compatibility, install, update, and uninstall, data protection, and crash recovery.

Where the controls differ

QuestionEmbeddedWebApplication
Real environmentTarget board, PCB revision, BSP, firmwareBrowser, API, database, cloud, and networkOS, GPU or driver, device permissions
Key design recordsSchematic, interface timing, memory ownershipAPI schema, trust boundary, data modelUI state, event loop, data and plugin model
Main risksCache errors, bad frames, timing, power lossBroken access control, failed migration, capacity, privacyJank, incompatibility, data lost on upgrade
Core verificationHost + target + HIL + soak and fault testsContract + integration + E2E + load and securityUnit + UI + OS matrix + install and upgrade
Release assetsImage, DTB, BSP, board matrix, and hashesImage, DB migration, rollout, monitoring, and restoreInstaller, signature, support matrix, and rollback
Example: every algorithm-thread unit test passing on RK3588 does not prove that the sensor, PCIe, DMA, cache, and end-to-end timing are healthy. An API unit test does not prove that deployed authorization, the database migration, or the login flow is correct.
07 · OPERATION RECIPES

Four workflows you will actually use

A. New project: design and layout before code

Run from the repository; replace the path 
python devflow-guide/scripts/devflow.py inspect --root ./my-project
python devflow-guide/scripts/devflow.py init --root ./my-project \
  --profile embedded --assurance standard --dry-run
# After reviewing the planned files and approving them:
python devflow-guide/scripts/devflow.py init --root ./my-project \
  --profile embedded --assurance standard
python devflow-guide/scripts/devflow.py audit --root ./my-project

Fill requirements, architecture, interfaces, and the test strategy first. A TODO warning means the template is still unfinished. A person then decides which proofs of concept or board tests are required before design or coding continues.

B. Existing project: adopt it, do not regenerate it

An existing repository must pass --adopt 
python devflow-guide/scripts/devflow.py inspect --root ./existing-repo
python devflow-guide/scripts/devflow.py init --root ./existing-repo \
  --profile web --assurance high --adopt --dry-run
# Check that existing specifications were mapped. After approval, drop --dry-run:
python devflow-guide/scripts/devflow.py init --root ./existing-repo \
  --profile web --assurance high --adopt

If a README.md, SRS, API schema, or architecture document is already authoritative, do not copy its content into a second conflicting version. Check the .devflow.json map first.

C. One feature: requirement, small task, proof in the same PR

Write the REQ and acceptance criteria. If the change is a cross-module interface or architecture decision, add or update an ADR and the contract. Then open a TASK that names the source files, tests, and documents in scope. After implementation, run the real build and tests, report what was not run, and open a PR for a person to review.

Review draft 
Use $devflow-guide to implement TASK-ISP-007:
1. Check the current main SHA, the linked REQ, and the ADR status first.
2. Touch only the scope named by the TASK. Interface changes update the contract and tests.
3. Run the build, unit tests, and integration tests the project can actually execute.
4. Report PASS, FAIL, or UNKNOWN with the command, environment, and real log or URL.
5. Do not merge the PR, and do not treat a Proposed ADR as Accepted.
6. Submit a review note: files changed, risks, missing evidence, and the next step.

D. Release candidate: local preflight plus the real external gate

Read-only checks 
python devflow-guide/scripts/devflow.py audit --root ./my-project --strict
python devflow-guide/scripts/devflow.py gate --root ./my-project --stage design
python devflow-guide/scripts/devflow.py gate --root ./my-project --stage merge
python devflow-guide/scripts/devflow.py gate --root ./my-project --stage release

The difference that matters: the script can check local files, trace rows, and Git state. It cannot certify remote CI, reviews, hardware trials, or approvals. READY_FOR_HUMAN_REVIEW still requires confirmation in the real pull request, CI, and release system.

08 · CLI REFERENCE

What the script really checks, and what it can only call unknown

devflow.py uses the Python 3.9+ standard library on Windows, Linux, and macOS. It does not run the project build, does not use the network, and does not perform dangerous Git writes. Every stage gate is a local preflight opinion.

CommandWrites to the project?What it can checkWhat it must not claim
inspectNoDirectory clues, a type suggestion, and the Git baselineThat it fully understands the business
init --dry-runNoFiles it would create or mapThat initialization already happened
init [--adopt]Only missing governance filesConfig plus templates that still need to be filled inThat requirements or design are approved
auditNoDocument map, path safety, placeholders, the trace CSV, and Git change hintsThat tests passed or that the code means the right thing
gate --stageNoStructural checks before design, merge, or releaseThat external CI or a person has approved it

How to read a typical result

BLOCKED

A required file is missing, a path is unsafe, evidence is absent, or a critical placeholder remains. Do not advance that stage as if it were ready.

REVIEW_REQUIRED

There is a warning or an item a person must confirm. Do not treat the result as fully usable.

LOCALLY_CONSISTENT

The local structure check found nothing wrong. That does not mean the implementation, performance, or remote CI passed.

READY_FOR_HUMAN_REVIEW

It is ready to hand to someone with authority. It is not formal approval.

Exit codes and CI

audit returns 2 on a structural error. With no errors, warnings usually return 0, and 1 when --strict is set. gate returns 2 when it blocks. A project may run audit --strict in CI according to its own risk. Do not let the script exit code replace real tests, pull-request approval, or release authorization.

For a wrapper or a monorepo, point --root at the scope that is actually governed. Read document_map in .devflow.json. Do not force a parent SRS onto an unrelated submodule.
09 · INTERACTIVE GATE LAB

Why a fully ticked checklist is still not release approval

This is a learning simulator. Switch the stage, tick evidence, and watch the local preflight change. It does not read a real repository, and it does not change Git, CI, or release state.

Ticking every box only means the simulated local check is complete. Real CI, target-board tests, and approval by an authorized person still have to be verified separately.

10 · PRACTICE

Three realistic cases: land the work without empty documents

Case 1: a PC ISP simulator

Requirement: the user can adjust Gamma and preview the result. When Gamma is disabled, the request must not be rejected by the enabled-state parameter rules. Design: state when a parameter takes effect, the pipeline input and output formats, the meaning of a state change, and the error codes. Record an ADR only if the rule crosses modules in a way that later readers must remember. Task: change the contract, the implementation, and the boundary tests together. Verification: cover enabled and disabled, illegal values, state updates while switching, and any performance figure the project actually requires. Release: a green build and a finished review do not mean the new contract has been released.

The smallest trace for this case

REQ-ISP-001 → the enabled condition in the interface contract → TASK-ISP-007 → the implementation PR → TEST-ISP-001 (positive and negative) → a real CI or human acceptance record. The identifiers are examples only.

Case 2: dual-channel capture and processing on RK3588

Requirement: hold the target frame rate on the confirmed sensor and board configuration, and do not let a slow consumer rewind frames. Architecture: the producer-consumer queue, ping-pong or ring buffers, DMA and cache ownership, timestamp alignment, and the drop policy. Verification: host tests for the data structure; on-target tests for multi-channel frame integrity, soak, start/stop, fault interruption, and temperature. Release: freeze the combination of BSP, kernel, DTB, user firmware, and board revision.

Case 3: a Qt H.265 player

Requirement: name the supported H.265 bitstream or container and the OS or decoder environment. On failure, return an error the user can recover from. Architecture: the playback state machine, decode thread, video rendering, buffer ceiling, and resource release. Verification: bitstream samples, close and reopen, hardware decode unavailable, device changes, and installer upgrade. Release: the built installer version must match the version the application shows. Check the signature, dependencies, and recovery path.

A task contract you can reuse

Task contract · all three profiles 
TASK_ID: TASK-<SCOPE>-NNN
TYPE: feature / defect / refactor / hotfix / docs
REQ: linked requirement IDs
BASELINE: baseline branch and the real current SHA
GOAL: the observable result and why it matters
SCOPE: modules that must change, and what must not change
DESIGN: architecture, ADR, and interface contract, each with its status
ACCEPTANCE: normal and illegal inputs, and measurable criteria
TEST: the real conditions for unit, integration, target, HIL, or E2E
RISK: safety, compatibility, data, timing, upgrade, and rollback
OUTPUT: source, the necessary documents, tests, and evidence
STOP: cannot verify, interface conflict, or an unauthorized dangerous action
11 · TROUBLESHOOTING

Where workflow governance usually goes wrong

Does every one-line change need an ADR?

No. An ADR records a significant architecture choice whose reason must still be clear later. An ordinary fix belongs in the issue or pull request. How much detailed design you write depends on complexity and risk.

I already have a lot of documents. Why not just paste them into the templates?

One requirement or protocol cannot have two conflicting authorities. Run --adopt --dry-run first, keep the existing specification, and add any unrecognized path to .devflow.json by hand.

Detection says hybrid or ambiguous. What now?

Choose the scope from the runtime, the deliverable, and the subproject. A repository that contains firmware, a backend, and a Qt GUI needs an explicit cross-system contract. Do not force one profile onto all of it.

The test machine or target board is unavailable. Can I still open a PR?

Say exactly what did not run, and the risk. Whether it may merge is decided by the project gate and the person who owns that decision. A high-assurance or safety-related change may have to stop. Host unit tests are not HIL.

Why does the release preflight never print "automatically approved"?

Release depends on whether remote CI is genuine, who owns the artifact, independent approval, the target environment, and actions that may be irreversible. An offline local script has neither the authority nor the information, so those items stay UNKNOWN.

Can we still use Git Flow, trunk-based development, or Scrum?

Yes. The skill does not impose a branch model or an agile ceremony. It asks for small reviewable changes, a reliable merge gate, a version baseline, and traceable evidence. Pick the flow that matches how the team delivers.

Can this be used directly for a safety certification such as ISO 26262 or IEC 62304?

No. This general skill is not a compliance certificate. A regulated project still needs the applicable standard, its own process system, tool qualification, and an authorized independent assessment. This package is only a general engineering starting point.
